## Main recommendation

Don't copy the existing pattern. Today each capability (bulk, scheduled, template, media, V2) is its own endpoint with up to 14 flat optional parameters. Adding two channels the same way would mean either two more endpoints that each need all of those capabilities, or a matrix of `/sendWhatsAppBulk`, `/sendRCSScheduled` and so on.

Instead, make the two new endpoints **channel-specific but capability-complete**:

- Bulk, scheduling, templates and media are **fields**, not separate endpoints.
- Channel-specific content goes in a **typed `content` object** rather than flat optional parameters.
- The envelope is identical on both endpoints, so a shared validator and handler can serve them.

You keep the `/sendWhatsApp` and `/sendRCS` names you planned. The shape is also a template for later migrating the legacy endpoints.

## Shared envelope

`POST /sendWhatsApp` and `POST /sendRCS` share these headers and fields.

**Headers**
- `Authorization`
- `Idempotency-Key` (recommended; required for bulk)

**Top-level fields (8, not 14)**

| Field | Type | Notes |
|---|---|---|
| `from` | string | WhatsApp: business phone number ID. RCS: `agent_id`. |
| `to` | string | E.164. Mutually exclusive with `recipients`. |
| `recipients` | array | Bulk, max 1,000. Each has `to`, optional `variables` and `client_reference`. |
| `content` | object | Discriminated by `content.type` (see below). |
| `schedule_at` | RFC 3339 | Optional. Must be in the future, within 30 days. |
| `client_reference` | string | Your correlation ID, echoed in webhooks. |
| `callback_url` | URL | Overrides the account default for status events. |
| `metadata` | object | Up to 10 key/value pairs, echoed back. |

**Response: `202 Accepted`**
```json
{
  "batch_id": "bat_123",
  "channel": "whatsapp",
  "messages": [
    { "message_id": "msg_abc", "to": "+15551234567", "status": "queued" }
  ]
}
```
In bulk, invalid recipients are rejected per item in `messages[].error`. The request returns `202` as long as at least one recipient is accepted, and `400` only if all are invalid.

**Status webhooks** use the same event schema for both channels: `queued → sent → delivered → read | failed`. Failures carry a normalized `error.code` plus the provider's raw code. `read` is only emitted when the channel reports it.

## `/sendWhatsApp` content types

`content.type` is one of:

- **`text`**: `{ "type": "text", "body": "...", "preview_url": true }`
- **`template`**: `{ "type": "template", "name": "order_update", "language": "en_US", "variables": { "1": "Sam", "2": "#4411" } }`
- **`media`**: `{ "type": "media", "media_type": "image|video|audio|document", "url": "...", "caption": "...", "filename": "..." }`
- **`interactive`**: `{ "type": "interactive", "body": "...", "buttons": [ ... ] }` (up to 3 reply buttons, or a list)
- **`location`**: `{ "type": "location", "lat": ..., "lng": ..., "name": "..." }`

**WhatsApp rules to enforce server-side**
- Outside the 24-hour customer-service window, only `template` is allowed. Otherwise return `422 template_required`.
- Validate template name, language and variable count against approved templates before accepting.
- Media is supplied by `url` or a previously uploaded `media_id`. Check type and size limits at request time.

## `/sendRCS` content types

- **`text`**: `{ "type": "text", "body": "..." }`
- **`rich_card`**: `{ "type": "rich_card", "title": "...", "description": "...", "media": { "url": "..." }, "actions": [ ... ] }`
- **`carousel`**: `{ "type": "carousel", "cards": [ ... ] }` (2–10 cards)
- **`media`**: `{ "type": "media", "url": "...", "content_type": "image/jpeg" }`

**RCS-specific fields**
