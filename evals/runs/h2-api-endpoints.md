# Design: `/sendWhatsApp` and `/sendRCS`

I haven't looked at your codebase, so this is a contract-level design. I'd change one thing from the current pattern: don't give each new endpoint the `/sendBulk`, `/sendScheduled`, `/sendTemplate`, `/sendWithMedia` and `/sendV2` variants. That would make 12 endpoints, each with about 14 optional parameters. Instead, make bulk, scheduling, templates and media fields on one request body per channel.

## Shared envelope

Both endpoints share these fields.

| Field | Type | Notes |
|---|---|---|
| `to` | string or string[] | E.164. An array (max 1000) replaces `/sendBulk`. |
| `from` | string | Sender ID. For WhatsApp, a business phone number ID. For RCS, an agent ID. |
| `content` | object | Channel-specific; see below. |
| `scheduleAt` | ISO 8601 | Replaces `/sendScheduled`. Must be in the future and at most 30 days out. |
| `clientRef` | string | Your correlation ID, echoed in webhooks. |
| `idempotencyKey` | string | Also accepted as an `Idempotency-Key` header. Retries within 24h return the original result. |
| `callbackUrl` | URL | Optional per-request override of the account webhook. |
| `validityPeriod` | seconds | TTL after which the message is dropped. |

The body has 7 top-level fields instead of 14 flat optionals. Everything channel-specific lives under `content`, which is a discriminated union on `type`.

## POST /sendWhatsApp

`content.type` is one of:
- `text`: `{ body, previewUrl? }`. Only valid inside the 24h customer-service window.
- `template`: `{ name, language, components: [{ type, parameters[] }] }`. Required to start a conversation outside the window.
- `media`: `{ kind: image|video|audio|document|sticker, url | mediaId, caption?, filename? }`
- `interactive`: `{ kind: buttons|list, body, action }`, with up to 3 reply buttons or a list of up to 10 rows.
- `location`: `{ lat, lng, name?, address? }`

Validation rules:
- Return `422 template_required` for free-form content outside the window, rather than letting it fail downstream.
- Validate template name, language and parameter count against approved templates at request time.
- Require `optIn: true` or an opt-in record on the account for the recipient. Reject with `403 no_opt_in` otherwise.

## POST /sendRCS

`content.type` is one of:
- `text`: `{ body }` (max 3072 chars)
- `richCard`: `{ title, description, media?, suggestions[] }`
- `carousel`: `{ cardWidth, cards[2..10] }`
- `media`: `{ url, contentType, thumbnailUrl? }`

`suggestions[]` (max 11) are either `reply { text, postbackData }` or `action { type: openUrl|dial|location|calendar, ... }`.

RCS-only fields:
- `fallback`: `{ channel: "sms", body, from }`. If the handset isn't RCS-capable or delivery fails, send SMS.
- `trafficType`: `transactional | promotional | otp`. Carriers price and route these differently.
- `GET /rcs/capability?to=...` is a companion endpoint so customers can pre-check device support.

# Design: WhatsApp and RCS sending

## Recommendation

Don't add two more 14-parameter endpoints. The existing six (`/send`, `/sendBulk`, `/sendScheduled`, `/sendTemplate`, `/sendWithMedia`, `/sendV2`) split by feature: bulk, scheduled, template, media. Those features apply to every channel. If you add `/sendWhatsApp` and `/sendRCS` the same way, you get a channel × feature matrix (bulk WhatsApp, scheduled RCS, and so on) that you can't maintain.

Instead, make the channel a field and keep the feature options shared.

## Proposed API

```
POST /v2/messages          create one message, or a batch
GET  /v2/messages/{id}     status
POST /v2/messages/capabilities   "can this number receive RCS/WhatsApp?"
```

If you want the names `/sendWhatsApp` and `/sendRCS` for marketing or migration reasons, ship them as thin aliases. They would be the same handler with `channel` preset, and the same schema.

### Request shape

Shared fields stay at the top level. Anything channel-specific goes in its own object.

```json
{
  "channel": "whatsapp",
  "from": "wa_sender_123",
  "to": ["+15551234567"],
  "content": { "type": "text", "body": "Your order shipped" },
  "schedule_at": "2026-10-12T09:00:00Z",
  "idempotency_key": "ord-9981-ship",
  "callback_url": "https://example.com/hooks/msg",
  "fallback": [{ "channel": "sms" }],
  "whatsapp": { },
  "rcs": { }
}
```

- **`channel`**: one of `sms`, `whatsapp`, `rcs`. It is required.
- **`to`**: an array, so the bulk case needs no separate endpoint. Set a hard cap such as 1,000 and return per-recipient results.
- **`content.type`**: `text`, `media`, `template`, `interactive` (WhatsApp), or `rich_card` / `carousel` (RCS). This replaces `/sendTemplate` and `/sendWithMedia`.
- **`schedule_at`**: optional. It replaces `/sendScheduled`.
- **`idempotency_key`**: also accepted as a header. Retries must not double-send.
- **`fallback`**: an ordered list of channels to try if delivery fails or the recipient isn't reachable. The typical case is RCS → SMS.

### WhatsApp specifics

- **Templates**: Business-initiated messages outside the 24-hour customer-service window must use a pre-approved template.
  ```json
  "content": { "type": "template", "name": "order_shipped", "language": "en_US",
               "variables": ["Saad", "#9981"] }
  ```
- **Window rule**: Free-form `text` is only valid inside the 24-hour window. Return `422 outside_service_window` with a hint to use a template. Don't let it fail silently downstream.
- **Interactive**: reply buttons (up to 3) and list messages.
- **Media**: reference a `media_id` or an `https` URL, with a caption. Validate MIME type and size per channel up front.
- **Opt-in**: require `"opt_in": { "source": "...", "timestamp": "..." }`, or verify consent server-side per account. Meta enforces this, and violations put the customer's sender quality at risk.

### RCS specifics

- **Agent**: `from` is the RCS agent ID.
- **Content types**: `text`, `rich_card` (title, description, media, up to 4 suggestions), and `carousel` (2–10 cards).
- **Suggestions**: replies and actions (open URL, dial, calendar event, share location).

  ```json
    { "type": "reply", "text": "Track order", "postback": "track_9981" },

  ```

- **Billing**: RCS billing differs for basic and rich messages. Return the billed `type` in the response.
