# Recommended architecture: a modular monolith on managed services

Your load is small. 200 customers × ~300 invoices is about 60k invoices a month, or roughly one every 40 seconds on average. A single Postgres database and a small app tier handle that easily. With four people, your main constraint is operational overhead, not scale, so I'd avoid microservices and Kubernetes.

## Core stack

| Layer | Choice | Why |
|---|---|---|
| App | One deployable monolith in a language the team already knows (TypeScript/Node, Rails, Django, or similar) | One repo, one deploy, one thing to debug |
| Database | Managed Postgres (RDS, Cloud SQL, or Neon/Supabase) | Invoicing needs transactions, constraints, and relational integrity |
| Background jobs | A Postgres-backed queue (pg-boss, Oban, GoodJob, or Solid Queue), or Redis with Sidekiq/BullMQ if you already want Redis | PDF generation, emails, reminders, and webhook processing run here |
| Hosting | A PaaS (Render, Fly.io, Railway, Heroku) or ECS Fargate/Cloud Run | No cluster to operate |
| File storage | S3-compatible object storage for generated PDFs and attachments, served via signed URLs | Keeps blobs out of the database |
| Email | Postmark, SES, or SendGrid | Invoice delivery and reminders |
| Frontend | A web SPA or server-rendered app in the same codebase, behind a CDN | One team can own it end to end |
| Observability | Sentry, structured logs, uptime checks, basic metrics (Datadog, Grafana Cloud, or similar) | Enough to catch problems without a platform team |

Run two process types from the same codebase: **web** and **worker**. Run at least two instances of each in production, plus a staging environment.

## Internal module boundaries

Keep clear boundaries inside the monolith so you can extract a service later if you ever need to:

- **Accounts/Tenancy:** organizations, users, roles, and API keys
- **Customers/Catalog:** the client records and products/line items that your tenants bill
- **Invoicing:** drafts, numbering, taxes, status lifecycle, PDF rendering, and recurring schedules
- **Payments:** Stripe integration, payment records, reconciliation, and refunds
- **Notifications:** email delivery and reminders
- **Audit/Reporting:** audit log, exports, and aging reports

## Multi-tenancy

Use a shared database and schema with an `organization_id` on every tenant-owned table. At your scale this is the simplest option. To prevent cross-tenant data leaks:

- Enforce it with Postgres row-level security, or at minimum a tenant-scoped query layer.
- Add tests that specifically try to read another tenant's data.
- Don't plan on a database per customer. It adds a lot of migration and operational cost for no benefit here.

## Stripe integration (the part to get right)

The first decision is which Stripe model you use. The answer depends on whose money you're moving:

- **Stripe Connect:** your customers' clients pay your customers, and you may take a fee. This is likely the right model for a B2B invoicing SaaS, because money lands in each business's own account. Use Standard or Express accounts to keep your compliance burden down.
- **Plain Stripe Billing:** you charge your customers a subscription for using your product. You'd need this in addition to Connect.

Clarify this early, because it affects your data model and your regulatory exposure.

Practices that apply either way:

- **Webhooks are the source of truth** for payment state. Don't rely on the redirect after checkout.
- **Verify signatures.** Persist each raw event first, return 200 quickly, and process it in a worker.
- **Make handlers idempotent.** Dedupe on Stripe's event ID, because events can be duplicated or arrive out of order.
- **Send idempotency keys** on every API call that creates something.
- **Run a nightly reconciliation job** that compares your records against Stripe, to catch missed webhooks.
- **Use Stripe Checkout or Payment Links with Stripe-hosted pages** wherever possible, so card data never touches your servers (this keeps you at PCI SAQ-A).
- **Store money as integer minor units plus a currency code.** Never use floats.

## Invoicing-specific design points

These tend to cause trouble later if you skip them:

- **Gapless, per-tenant invoice numbering** assigned at finalization, not at draft creation. Many jurisdictions require it. Use a locked counter row inside a transaction.
- **Immutability after issue.** A finalized invoice can't be edited. Corrections go through credit notes or new invoices.
- **A state machine** (draft → sent → partially paid → paid / void / overdue) with explicit allowed transitions.
- **Tax handling:** start with simple per-tenant tax rates. If you sell across jurisdictions, consider Stripe Tax or a similar provider rather than building your own.
- **An append-only audit log** of invoice and payment events. Customers will ask for it, and you'll need it for disputes.
- **Deterministic PDF rendering** that is stored once at finalization, so a re-download always matches what was sent. Use headless Chromium or a library such as WeasyPrint or react-pdf, run in a worker.

- Authentication: use a vetted provider or library (Auth0, WorkOS, Clerk, or your framework's built-in). Support MFA, and plan for SSO later because B2B buyers ask for it.
- Role-based access per organization (owner, admin, member, read-only).

- Enable automated database backups with point-in-time recovery, and actually test a restore.
- You'll hold financial and personal data, so plan for GDPR-style export and deletion. Retention rules for invoices often conflict with deletion requests, so decide on a policy early.

## Delivery and operations

- CI/CD on every merge, with automated tests and zero-downtime deploys.

- Database migrations that are backward-compatible, so you can deploy without downtime.

- Microservices, Kubernetes, and event streaming (Kafka)

- **Customers/Clients:** the contacts your tenants invoice.
- **Invoicing:** invoices, line items, taxes, numbering, status lifecycle (draft → sent → paid/void), credit notes.
- **Payments:** Stripe integration, payment records, reconciliation.
- **Billing (your own SaaS subscription):** keep it separate from invoice payments.
- **Documents & notifications:** PDF rendering, emails, reminders.
- **Audit log:** an append-only record of every state change.

## Key design decisions

1. **Multi-tenancy:** a shared database and schema with `org_id` on every table. Enforce isolation with Postgres Row-Level Security as a backstop to app-level scoping. 200 tenants doesn't justify schema-per-tenant or database-per-tenant.
2. **Stripe model:** use **Stripe Connect** (Standard or Express accounts) if your customers collect money from *their* clients through you. That is the usual case for B2B invoicing. If you only charge your customers for your own subscription, plain Stripe Billing is enough. **Decide this first**, because it drives compliance, onboarding, and fee flows.
3. **Webhooks are the source of truth for payment state.**
   - Verify signatures.
   - Store each raw event, deduplicated by Stripe event ID.
   - Process it asynchronously and idempotently.
   - Send idempotency keys on all outbound Stripe calls.
   - Run a periodic reconciliation job against Stripe to catch missed events.
4. **Money correctness:** store amounts as integer minor units plus a currency code. Never use floats. Make issued invoices immutable (corrections go through credit notes). Assign gap-free per-tenant invoice numbers inside a transaction.
5. **Tax and compliance:** decide early whether to use Stripe Tax or a tax library. Also check your target markets for e-invoicing mandates (e.g. EU/Peppol) and data-retention rules, since these can shape the data model.
6. **PDFs:** render asynchronously (headless Chromium or a library), store the PDF in object storage, and keep the rendered artifact tied to the issued invoice version.
7. **Security basics:** never store card data (Stripe handles it), encrypt at rest, and use least-privilege IAM, secrets in a manager, and MFA for staff. Add an audit trail for admin actions.

## Environments & delivery

- Local (Docker Compose), staging (Stripe test mode), and production.

- Daily backup restore tests. A backup you haven't restored isn't a backup.

**Recommendation:** Build a modular monolith: one web app, one background worker from the same codebase, and one managed Postgres. Rent everything that isn't your core experience: payments, email, auth, hosting. Your peak load is about 60,000 invoices a month, roughly 2 an hour on average, so anything beyond this would be complexity for a team of four to maintain.

**Experience and quality bar**
- **Experience:** A business creates an invoice in under a minute, sends it, and gets paid without chasing.
- **Integrity:** An invoice or payment is never lost, duplicated, or wrong. Money is the hard requirement.
- **Latency:** Pages respond in under 300 ms at p95. Sending and PDF generation run in the background, with status shown in the UI.
- **Availability:** A 99.9% target is enough. An hour of downtime is annoying, not catastrophic, as long as webhooks are replayed afterward.
- **Scale:** About 200 tenants and under 100k invoices a month. One small Postgres instance handles this comfortably.

**Design**
- **App:** One deployable (for example Rails, Django, or Next.js with a typed backend, whichever the team knows best) on a PaaS such as Render, Fly, or AWS App Runner. There is no Kubernetes and no microservices.
- **Database:** Managed Postgres is the single source of truth.
- **Jobs:** A Postgres-backed queue (Solid Queue, Oban, GoodJob, or pg-boss) runs PDF rendering, email, reminders, and webhook processing. There is no Redis, because nothing here needs it.
- **Files:** Object storage (S3 or R2) holds the PDFs. PDFs can be rebuilt from invoice data, so treat them as derived.
- **Payments:** Stripe, with its hosted payment page so card data never touches you. Webhooks are verified, stored first, then processed by the worker.
- **Email:** Postmark or SES, with a verified sending domain and bounce handling.
- **Auth:** A managed provider or a well-maintained library, with 2FA and roles per tenant (owner, member).

**Domain rules to get right early**
- **Money:** Store integer minor units plus a currency code. Never use floats.
- **Invoices:** Once sent, an invoice is immutable. Corrections are credit notes. Numbering is sequential per tenant, with no gaps.
- **Payment state:** Derive it from Stripe events and keep an append-only ledger of payments.
- **Tax:** Model tax lines explicitly from day one, even if you only support simple rates at launch.

**Safeguards (non-negotiable)**
- **Tenant isolation:** `tenant_id` on every row, enforced with Postgres row-level security and not just in application code. Add tests that try cross-tenant reads.
- **Idempotency:** Webhook handlers dedupe on the Stripe event ID. Outbound Stripe calls carry idempotency keys, and email sends are keyed per invoice and action.
- **Validation and secrets:** Validate all input at the boundary. Keep secrets in the platform's secret store, with separate Stripe test and live keys.
- **Backups:** Point-in-time recovery is on, and you run a restore drill before launch and then quarterly.
- **Migrations:** They are versioned and reversible, and they run in CI against a copy of the schema.
- **Observability:** Structured logs and error tracking (Sentry). Alert on webhook failures, queue lag, failed sends, and the hero path (create → send → pay) breaking.
- **Tests:** Cover the hero path, the Stripe webhook edge cases (duplicates, out of order, retries), and the money invariants.

- **Read replica or separate reporting store:** Reporting queries slow the app, or p95 exceeds 300 ms.
- **Separate worker service:** Job volume starves web requests.
- **Redis or cache:** A measured hot read path justifies it.
