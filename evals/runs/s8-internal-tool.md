# Meeting room booking tool: proposal

## First, a check
If you're on Google Workspace or Microsoft 365, **room resources in the shared calendar** already block double-booking with no build. If you have a reason to build anyway (no suite, want a wall display, or want a simple custom flow), the plan below fits in about a week.

## Architecture
Keep it small. For 15 people and 2 rooms, one service and one database is enough.

- **App:** a single web app (for example Node/TypeScript or Python/FastAPI) that serves a lightweight front end and a JSON API. There's no microservice split and no separate SPA build unless you want one.
- **Database:** Postgres, or SQLite if you want the least ops. The data is tiny: `users`, `rooms`, `bookings`.
- **Auth:** sign-in with your existing Google or Microsoft work accounts (OIDC), restricted to your company domain. That avoids passwords and gives you names for free.
- **Hosting:** one small container on Fly, Render, or an office box, behind HTTPS. Add a daily DB backup.
- **Notifications:** email, plus optionally a Slack webhook.

### Preventing double-booking
The database should enforce this, not the UI.
- **Postgres:** an exclusion constraint on `(room_id, tstzrange(start, end))` with `&&`. Overlapping inserts then fail atomically, even with simultaneous requests.
- **SQLite:** do the overlap check and insert in one `BEGIN IMMEDIATE` transaction.
- **On conflict:** the API returns a 409 with who holds the slot, and the UI shows that message.
- **Overlap rule:** use half-open intervals `[start, end)`, so a 10:00–11:00 booking and an 11:00–12:00 booking don't clash.

### Data model
- `rooms(id, name, capacity, equipment)`
- `bookings(id, room_id, user_id, title, start, end, created_at, cancelled_at)`
- Store times in UTC and display them in the office timezone.
